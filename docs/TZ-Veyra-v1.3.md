## 1. Контекст

Veyra — инструмент для поиска расхождений, противоречий, невыполненных обещаний и слепых зон в стратегических материалах коммерческого блока Avito. Аудитория — аналитики и менеджеры ASD Goods, потенциально весь коммерческий блок.

Источники данных — **два типа**:
- **Документы:** 500+ стратегических документов (Confluence, частично docx/pdf).
- **Дашборды и метрики:** редаши и DWH-данные по стримам команды (см. Возможность 7).

Данные конфиденциальные — это отдельный фактор архитектуры (см. Принцип 5).

**Целевой пользовательский сценарий:**

```
Пользователь: "Проверь инициативу X на согласованность с корпусом"
Veyra:        список расхождений с цитатами и ссылками на источники
```

**Метафора Алексея — «бульон»:** загрузить по максимуму материалов и собрать переиспользуемый субстрат знаний, из которого дальше «варится» любой ответ — разбор инициативы, поиск противоречий, проверка обещаний.

Дополнительно (опционально, Фаза 4): фоновый проход по корпусу с проактивными уведомлениями о новых расхождениях.

## 2. Принципы реализации (не нарушать)

1. **Никакой галлюцинирующий детектор не попадает в прод.** Skeleton MCP можно строить параллельно с гейтом, но реальная логика детектора заливается в MCP-сервер только после прохождения гейта. До гейта эндпоинты возвращают заглушки. Сервис не регистрируется в production-режиме MCP Hub — только staging/alpha.

2. **Использовать готовую инфру Avito, не строить свою.**
   - LLM: внутренний gateway `https://llm-gateway.k.avito.ru/v1` (OpenAI-совместимый), модель `vsellm/anthropic/claude-opus-4.7`.
   - Документы: Confluence MCP из mcp-hub.
   - Дашборды/метрики: `dwh-redash-mcp`, `querypad`, `trisigma-mcp` из mcp-hub.
   - Хостинг сервиса: PaaS Avito.
   - Регистрация: avito mcp-registry + skills-hub.

3. **Veyra = слой детекторов, а не «ещё один продукт».** Не строить отдельный сайт/UI. Точка входа — skill в Avito AI, плюс опционально n8n workflow для проактивности.

4. **Образец для упаковки skill** — `quality-metrics` (`stash.msk.avito.ru/agent/qa-skills`). Структура `SKILL.md` + `scripts/` + `references/`, два режима (диалог + Confluence-отчёт).

5. **Конфиденциальность.** Индекс с эмбеддингами/TF-IDF и любые выгрузки метрик — производное от конфиденциальных данных. Хранение только в авторизованном сервисе (MCP-сервер с Keycloak), не в общем S3, не локально у пользователей.

6. **Детектор и генератор валидируются по-разному.** Детектор (находит факт о корпусе — расхождение, обещание, пробел) проходит гейт recall/precision. Генератор/обогатитель (пишет текст, тянет внешние данные) проходит свой бар качества. Не смешивать в одну метрику. См. раздел 3.

## 3. Возможности (полный набор — задача Алексея, бриф 07.05.2026)

Возможности **не однородны по риску** и валидируются по-разному.

| # | Возможность | Класс | Данные | Риск | Как валидируется | Фаза |
|---|---|---|---|---|---|---|
| 1 | Числовые расхождения | детектор | корпус | низкий — детерминированная группировка метрик | гейт, трек 5.1 | 1 |
| 2 | Логические расхождения | детектор | корпус | **высокий** — галлюцинация связей | гейт, трек 5.2 (отдельно) | 1 |
| 3 | Невыполненные обещания | детектор | корпус + даты | средний | гейт, трек 5.3 | 1–2 |
| 4 | Серые зоны (пробелы в документах) | детектор | корпус | **очень высокий** — доказательство отрицания | гейт, трек 5.4 | 2 |
| 5 | Рыночный контекст | обогатитель | внешний веб | средний — выдуманные источники, утечка | свой бар: каждое утверждение = рабочая ссылка | 3 |
| 6 | Помощь в написании | генератор | корпус + стиль | средний | не contradiction-гейт; черновик прогоняется через детекторы 1–4 | 3+ (опц.) |
| 7 | Дашборды и слепые метрики | интеграция + детектор | дашборды/DWH | A: низкий · B: высокий | A: ручной бенчмарк · B: гейт, трек 5.5 | 2–3 |

**Ключевой вывод:** возможности 1–4 и 7B — детекторы, все идут через гейт раздельно. Возможности 5, 6, 7A — не детекторы, у них свои бары качества.

### 3.1. Возможность 1 — Числовые расхождения
Одна метрика, один период, одна единица — разные значения в разных документах. Детектор по корпусу, детерминированная группировка. Риск низкий.

### 3.2. Возможность 2 — Логические расхождения
Противоположные подходы/тезисы по одной теме («здесь вы говорите одно, здесь другое»). Детектор по корпусу, LLM-анализ. **Риск высокий** — Claude на длинных стратегиях склонен выдумывать логические связи.

### 3.3. Возможность 3 — Невыполненные обещания
Обещание в документе A, чей статус «не выполнено» виден в документе B или по срокам. Детектор по корпусу + временная привязка.

### 3.4. Возможность 4 — Серые зоны (пробелы в документах)
Темы и риски, которые упомянуты/подразумеваются, но не закрыты планом — «провалили между стульев и забыли». Детектор по корпусу. **Риск очень высокий** — «чего-то нет» требует доказать отрицание. Жёсткое правило: каждый пробел сопровождается **охватом поиска** (что и где проверено), иначе находка отбрасывается. Формулировка детектора шире, чем «пропущенные метрики» — это и слепые возможности/направления.

### 3.5. Возможность 5 — Рыночный контекст
Кросс-опыление с рынком: внешние данные сопоставляются с внутренними документами при разборе инициативы. **Не детектор** — гейт расхождений неприменим. Свой бар: каждое рыночное утверждение несёт рабочую ссылку на источник; на проверке вручную сверяются N утверждений.
**Конфиденциальность критична:** запрещено отправлять сырой текст конфиденциальных документов во внешний веб-поиск. Запросы строятся из обобщённых тематических терминов. Эндпоинт принимает обобщённую тему, не документ.

### 3.6. Возможность 6 — Помощь в написании
Помощь в написании инициативы/раздела в стиле команды. **Генератор.** Veyra не пишет документ автономно: (а) собирает grounded-факты из корпуса под тему, (б) даёт черновик в стиле команды, (в) сразу прогоняет черновик через `check_initiative`. Реализуется как расширение режима отчёта скилла.
> **Примечание:** этой возможности нет в брифе Алексея 07.05 — добавлена из кодовой базы и прошлых обсуждений. Первый кандидат на вырез из MVP при дефиците времени.

### 3.7. Возможность 7 — Дашборды и слепые метрики
Бриф Алексея дословно: «…чтобы код имел доступ к нашим всем дашбордам, чтобы была история метрик, динамики по стримам. И чтобы мы задали вопрос: какие метрики, на твой взгляд, могли бы быть ещё, на которые мы не обращаем внимания».

- **Часть A — ретрив живых метрик:** история метрик и динамика по стримам. Класс — интеграция; гейт не нужен, нужен ручной бенчмарк релевантности. Veyra-MCP вызывает `dwh-redash-mcp` / `querypad` / `trisigma-mcp`.
- **Часть B — слепые метрики:** «какие метрики стоит смотреть, но не смотрим». Это **детектор** (доказательство отрицания) → обязательно гейт, трек 5.5. Предложенная метрика привязывается к реальному стриму и реальному дашборду, иначе отброс.

Данные дашбордов конфиденциальны — то же хранение, что у индекса корпуса (Принцип 5).

## 5. Гейт детекторов — пять треков

Гейт проверяет **пять треков раздельно**. Метрики не усредняются: числовой трек может пройти, а логический провалиться — это разные решения.

**Входы:** 3 заранее выбранных документа из корпуса + размеченный вручную ground truth по каждому треку.

| Трек | Возможность | Ground truth (минимум) |
|---|---|---|
| 5.1 Числовой | 1 | 2 числовых расхождения |
| 5.2 Логический | 2 | 2 смысловых противоречия |
| 5.3 Обещания | 3 | 1 обещание со статусом «не выполнено» |
| 5.4 Пробелы | 4 | 1 серая зона (с охватом поиска) |
| 5.5 Слепые метрики | 7B | 1 метрика, которую не отслеживают, но должны (привязка к стриму+дашборду) |

**Что сделать:**
1. Проверить, что `index_docs.py` отрабатывает на 3 доках без ошибок.
2. Запустить `run_gate.py` на выборке.
3. Сравнить находки детектора с ground truth по каждому треку.
4. Записать метрики в `gate_report.md` — recall и precision **по каждому треку отдельно**. Каждая находка проверяема по точным цитатам из источника.

**Критерии прохождения (по каждому треку отдельно):**
- Recall ≥ 80%.
- Precision ≥ 70%.
- Все находки имеют точные цитаты из источника.

**Если трек не пройден:**
1. Разобрать false positives (что принято за находку, но не является).
2. Разобрать false negatives (что пропущено).
3. Доработать промпты детектора.
4. Повторить.
5. Если после 3 итераций трек не проходит — эскалация пользователю, возможен пересмотр самого детектора.
6. Skeleton MCP (Трек B) продолжает развиваться, но реальная логика непройденного детектора в него не заливается.

**Аутентификация на этой фазе:** временно личный ключ Anthropic пользователя через `.env`.

## 6. Фазы

### ФАЗА 1 — Параллельный запуск (1–3 дня)

Два трека одновременно.

**Трек A — Гейт детекторов (начать первым).** См. раздел 5. Цель — доказать, что детекторы находят настоящие расхождения и не галлюцинируют. Срок: полдня–день на трек.

**Трек B — Skeleton MCP-сервер (параллельно).** Цель — убрать инфраструктурный риск заранее (аппрув PaaS, Keycloak, требования mcp-registry).
1. Создать PaaS-сервис `veyra-mcp` (Python, FastAPI) — пустой шаблон.
2. Эндпоинты-заглушки: `check_initiative`, `find_contradictions`, `search_corpus`, `get_document` → `{"status": "not_implemented", "stub": true}`; `health()` → реальный 200 OK.
3. Подключить OAuth/Keycloak — без выдачи доступа кому-либо, кроме разработчиков.
4. Задеплоить на staging PaaS.
5. Draft PR в `mcp-registry` с пометкой `[ALPHA / WIP — endpoints return stubs]`. Не мерджить до прохождения гейта.

Чего НЕ делать на Фазе 1: не вызывать LLM из эндпоинтов; не подключать индекс; не мерджить в production mcp-registry; не звать пользователей.
Срок: 2–3 дня (зависит от аппрува PaaS). Owner: Денис + Злата, SLA — best-effort.

**DECISION POINT — гейт пройден?**
- Нет → возврат в Трек A. Skeleton остаётся skeleton.
- Да → Фаза 2.

### ФАЗА 2 — Наполнение (неделя 1–2, параллельные треки)

**Трек C — Переход на Avito LLM Gateway.** Предусловие: получен Bearer-токен (Анастасия Рысмятова / Олег Королёв).
1. Обновить `.env`: `LLM_BASE_URL=https://llm-gateway.k.avito.ru/v1`, `LLM_API_KEY=<sk-avi-…>`, `LLM_MODEL=vsellm/anthropic/claude-opus-4.7`.
2. Проверить: `curl -s -H "Authorization: Bearer $LLM_API_KEY" "$LLM_BASE_URL/models" | grep claude-opus-4.7`.
3. Если используется официальный SDK Anthropic — заменить на OpenAI-совместимый клиент (`openai` Python SDK с `base_url`).
4. Перезапустить гейт на gateway-ключе.
5. Критерий: результат гейта не отличается от Фазы 1 более чем на 5 п.п.

**Трек D — Индексация полного корпуса.**
1. Получить полный корпус (500+ документов).
2. Запустить `index_docs.py` на всём корпусе.
3. Сохранить артефакт индекса: TF-IDF (pickle vectorizer + matrix) или эмбеддинги (numpy/faiss); метаданные документов (id, title, url, last_modified) — отдельным JSON.
4. Загрузить артефакт в storage сервиса `veyra-mcp` (PaaS volume / managed storage).
5. Бенчмарк: 10 тестовых запросов «найди документы про X» → проверка релевантности руками.
6. Критерий: топ-5 содержит хотя бы один релевантный документ в 9 случаях из 10.

**Трек E — Наполнение MCP реальной логикой.** Предусловие: гейт пройден.
1. Заменить заглушки реальными вызовами:
   - `check_initiative(text)`: retrieval → топ-N доков → детектор → структурированный ответ;
   - `find_contradictions(doc_id)`: то же, вход — документ из корпуса;
   - `find_open_promises(scope)`: невыполненные обещания (после трека 5.3);
   - `find_gaps(scope)`: серые зоны с охватом поиска (после трека 5.4);
   - `search_corpus(query, top_k)`: чистый retrieval;
   - `get_document(doc_id)`: полный текст для просмотра цитат.
2. Подключить хранилище индекса.
3. End-to-end тест на staging: вызов через mcp-hub → ответ <30 сек на типичный документ.
4. Обновить PR в mcp-registry: убрать `[ALPHA]`, добавить описание и owners.
5. Аппрув mcp-registry → мердж → сервис в production-hub.

**Трек F — Драфт SKILL.md.** Может идти параллельно. Образец — `quality-metrics`, изучить его `SKILL.md` первым делом.
Структура: `veyra-skill/SKILL.md` + `scripts/check_init.py` + `scripts/report.py` + `references/README.md`.
`SKILL.md` description (триггеры):
```yaml
---
name: veyra
description: >
  Находит расхождения, противоречия и невыполненные обещания в стратегических
  документах коммерческого блока. Используй при запросах "проверь инициативу",
  "согласована ли стратегия", "нет ли противоречий с прошлыми решениями",
  "что мы обещали и не сделали". Работает с корпусом 500+ документов через
  MCP-сервер veyra-mcp.
---
```
Два режима: диалог (`check_initiative` → структурированный ответ с цитатами) и отчёт (Confluence-страница, 3-колоночная таблица: расхождение / источник / рекомендация).

**Трек G — Интеграция с дашбордами (Возможность 7A).**
1. Подключить `dwh-redash-mcp` / `querypad` / `trisigma-mcp` как источники метрик.
2. Эндпоинт `metrics_history(stream)` — история и динамика метрик по стриму.
3. Ручной бенчмарк релевантности.
Детектор слепых метрик (7B) реализуется в Треке E после прохождения трека гейта 5.5 и зависит от Трека G.

## 7. Технический стек

- **Язык:** Python 3.11+.
- **LLM:** Avito gateway (OpenAI-совместимый клиент, `openai` Python SDK).
- **Retrieval:** TF-IDF (sklearn) как baseline; эмбеддинги — только если TF-IDF недостаточен.
- **MCP-сервер:** FastAPI на PaaS Avito.
- **Хранилище индекса:** диск сервиса / managed storage.
