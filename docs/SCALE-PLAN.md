# План загрузки корпуса — 100→300 документов

**Дата:** 17 мая 2026 · **Старт загрузки:** понедельник–вторник
**Назначение:** аналитический план — как подготовить систему к корпусу
в 100–300 документов, что сделать по шагам, чем мерить, чего ждать.

---

## 1. Проверка системы перед масштабом

Проверка — **статическая** (импорт модулей + разбор кода). Это не
нагрузочный тест; поведение под реальным объёмом меряется гейтом после
каждой партии (§5).

- 41 модуль бэкенда + `veyra-mcp` импортируются без ошибок.
- `index_docs.py` — есть режимы первичной загрузки (сброс) и `--sync`
  (инкремент по хэшу содержимого).
- `retriever` — гибридный поиск (вектор + BM25 + RRF), кандидат-пул 60
  на запрос — по оценке кода, для 300 документов (~11 000 чанков) этого
  достаточно; фактический recall проверяется гейтом.
- veyra-mcp — 8 data-инструментов, ноль LLM на живом пути.
- Гейт (`run_gate.py`) — пригоден как монитор масштаба (см. §5).

Блокирующих структурных дефектов при статической проверке не выявлено.
Это не гарантия — реальная готовность подтверждается гейтом (§5–§6).

## 2. КЛЮЧЕВОЕ РЕШЕНИЕ — грузить с детекторами или без

Это главный выбор. Индексация документа = два этапа: (1) парсинг +
чанкинг + эмбеддинги — **локально, без LLM**; (2) детекторы (skills) +
бриф — **LLM-вызовы**. Этап 2 управляется флагом
`ENABLE_BACKGROUND_SIGNALS` в `.env`.

| | С детекторами (`=true`) | **Без детекторов (`=false`)** |
|---|---|---|
| LLM-вызовов на 300 док | ~1800+ | **0** |
| Нужен токен gateway | да — личный ключ не вывезет | **нет** |
| Время загрузки 300 док | часы + риск падения на кредитах/лимитах | **минуты** (только локальные эмбеддинги) |
| Результат | полный «бульон»: расхождения, обещания, брифы | корпус полностью **ищется**; «бульона» нет |
| Интерактив (Claude агентно) | работает | **работает** |
| Проактив (готовые таблицы расхождений) | работает | пусто — добавить позже |

### Рекомендация: грузить БЕЗ детекторов

Причины:
- **Не блокируемся на токене.** 300 документов индексируются за минуты,
  бесплатно, на любом железе. Корпус доступен для поиска сразу.
- **Это работает по новой архитектуре.** Интеллект — у Claude: он
  агентно ищет по корпусу и сам находит расхождения. Детекторы-на-сервере
  для интерактива не нужны (показано гейтом — находки делал Claude, а не
  детекторы).
- **«Бульон» довариваем потом.** Когда придёт токен gateway —
  отдельным проходом включаем детекторы и пересобираем таблицы. Это
  batch-операция, она не мешает уже работающему поиску.

Честная цена: пока детекторы не прогнаны, **проактивный слой пуст** —
MCP-инструменты `find_*_contradictions` вернут пустые таблицы. Но
**интерактив — главный сценарий — работает**: Claude находит расхождения
агентно по запросу.

---

## 3. Что значит «грузим без детекторов» — режимы системы

- `parsed_text` каждого документа кэшируется всегда (до этапа детекторов)
  → `get_document` (полный текст) и агентное чтение работают.
- Корпус >200K символов → full-text режим отключается; брифов нет
  (детекторы off) → система работает в **чистом retrieval-режиме**.
  Это и есть агентный путь — Claude тянет фрагменты и рассуждает.
- Поэтому **качество retrieval на масштабе — критический параметр**.
  Его и мерим (§5).

## 4. Пошаговый план загрузки

```
0. В .env:  ENABLE_BACKGROUND_SIGNALS=false
            (детекторы выкл — грузим быстро и бесплатно)

1. Партия 1 (~100 документов) → backend/data/docs/
   ВАЖНО: среди них должны остаться 3 эталонных документа гейта
   (Progress plan, Education strategy, B2C Journey) — иначе нечем
   мерить recall.

2. python3 scripts/index_docs.py        ← первичная: сброс + индексация
                                          всех (парс+чанк+эмбед, без LLM)

3. Поднять сервер → python3 scripts/run_gate.py --retrieval --runs 3
   → смотрим recall: находит ли retrieval 5 известных кейсов СРЕДИ 100
   документов (а не среди 3).

4. Партия 2 (до ~200):  новые файлы → backend/data/docs/
   python3 scripts/index_docs.py --sync   ← инкремент, без сброса
   перезапуск сервера → run_gate.py --retrieval снова

5. Партия 3 (до ~300):  то же — --sync → рестарт → гейт

6. Решение после каждой партии:
   recall ≥ 80% → растём дальше
   recall < 80% → СТОП, чиним retrieval до следующей партии
```

Примечание: после `--sync` сервер обязательно перезапускать — иначе его
ChromaDB-клиент не увидит новые чанки (разные процессы).

---

## 5. Как мерить масштаб — гейт как монитор

`run_gate.py` прогоняет 5 размеченных вопросов по 3 эталонным
документам. Пока эти 3 документа в корпусе — гейт меряет главное:
**не теряет ли retrieval известные находки, когда они зарыты среди
100/200/300 документов.**

- Recall держится ≥80% по мере роста → retrieval масштабируется.
- Recall падает → retrieval перестаёт поднимать нужные куски — это
  сигнал чинить поиск (а не повод грузить дальше).

Это честный замер, а не угадывание: каждая партия — это проверка.

**Готово к загрузке 100–300 (ничего доделывать не надо):**
- индексатор (`index_docs.py` + `--sync`);
- гибридный retrieval;
- veyra-mcp (8 data-инструментов);
- гейт как монитор масштаба.

  проактивного обхода (без него «найди ВСЕ противоречия» на 300 доках

- дашборды (Возможность 7);
- деплой veyra-mcp на PaaS, регистрация в mcp-hub.

## 7. Риски на масштабе и что делать

| Риск | Что делать |
|---|---|
| **Retrieval recall падает** на 200–300 документах | Гейт это поймает после партии. Лечение: реранкинг, тюнинг весов гибрида, лучший чанкинг таблиц. Не грузить дальше, пока не починено. |
| Время индексации (эмбеддинги 300 док на CPU ≈ 20–40 мин) | Разово, терпимо. Грузить партиями — заодно виден прогресс. |
| Битый документ (повреждённый docx/pdf) | `index_docs.py` ловит ошибку по документу, печатает `ОШИБКА`, продолжает. Один битый файл не валит загрузку. |
| ChromaDB staleness при `--sync` на живом сервере | Перезапускать сервер после каждой партии. |
| Проактив пуст (детекторы off) | Ожидаемо. Интерактив работает. «Бульон» — отдельным проходом под токен. |
| SQLite + мультиюзер | На загрузке/пилоте не проблема. Масштаб пользователей — Postgres, Фаза 3. |

## 8. Мониторинг во время загрузки

- `index_docs.py` печатает по каждому документу `→ N чанков` и итог
  `Готово … Ошибок: K` — следить за `ОШИБКА`.
- После загрузки — `corpus_stats` / `GET /api/docs/stats`: число
  документов должно совпасть с числом файлов.
- Сервер — `GET /health`; логи — `docker logs` / uvicorn stdout.
- Проверка Chroma: число чанков в `khronika_actual` примерно
  пропорционально числу документов. Коэффициент ~37 чанков/документ —
  грубая экстраполяция с выборки в 3 документа (111 чанков); на реальном
  корпусе он будет другим. Это ориентир «порядок величины», не норматив.

## 9. Резюме — что делаем с понедельника

1. `.env`: `ENABLE_BACKGROUND_SIGNALS=false`.
2. Грузим корпус **партиями** (100 → 200 → 300), `index_docs.py` затем
   `--sync`. Быстро, бесплатно, без токена.
3. После каждой партии — `run_gate.py --retrieval`, смотрим recall.
4. Recall держится → растём. Просел → чиним retrieval.
5. «Бульон» (детекторы) и структурный индекс — отдельным проходом,
   когда будет токен gateway.

Главное: **загрузка корпуса и получение токена развязаны.** Корпус
можно поднять и сделать полезным (агентный Claude поверх) уже в
понедельник, не дожидаясь токена. Токен нужен для проактивного слоя —
это следующий, отдельный шаг.
