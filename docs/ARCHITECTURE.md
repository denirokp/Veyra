# Veyra — архитектура и логика системы

**Версия документа:** 1.0 · 17 мая 2026
**Назначение:** единое описание логики, реализации, схем и границ Veyra.
Этот документ — источник правды по архитектуре; при расхождении с более
ранними заметками верен он.

---

## 1. Что такое Veyra

Veyra — корпоративная память коммерческого блока Avito. Её работа — два
типа вопросов: (1) **где стратегические документы спорят друг с другом**
— числовые расхождения, логические противоречия, невыполненные обещания,
пробелы «между стульев»; (2) **чего мы не видим** — неувиденные
возможности и гипотезы, которые ищутся сверкой корпуса с рынком и
дашбордами (см. `SYSTEM.md §2`, `TZ §3`). Не пишет документы вместо
человека, не заменяет поиск по Confluence — её ниша в **логике: где
документы спорят и чего в них не хватает**.

Доставляется не как отдельный сайт, а как **MCP-сервер** — набор
инструментов внутри помощника (Claude / Avito AI), которым уже
пользуется сотрудник.

---

## 2. Архитектура — три слоя

```
┌──────────────────────────────────────────────────────────────┐
│  СЛОЙ 3 — CLAUDE  (весь интеллект, на стороне клиента)        │
│  агентный цикл: ищет → читает → докапывается → сверяет        │
│  синтез ответа · написание · веб-поиск · анализ · вердикт     │
└───────────────────────────┬──────────────────────────────────┘
                            │ MCP (streamable-http)
┌───────────────────────────▼──────────────────────────────────┐
│  СЛОЙ 2 — veyra-mcp  (фасад данных, НОЛЬ LLM, ноль токенов)   │
│  search_corpus · get_document · list_documents                │
│  find_numeric_contradictions · find_logic_contradictions      │
│  find_open_promises · corpus_stats · health                   │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP (внутренний)
┌───────────────────────────▼──────────────────────────────────┐
│  СЛОЙ 1 — backend-движок                                      │
│  хранение документов · чанкинг · эмбеддинги · retrieval       │
│  индекс-время: детекторы (переходно — см. §9)                 │
│        │                              │                      │
│   ┌────▼─────┐                  ┌─────▼──────┐                │
│   │ ChromaDB │                  │  SQLite    │                │
│   │ вектора  │                  │ документы, │                │
│   │ кусков   │                  │ карточки   │                │
│   └──────────┘                  └────────────┘                │
└────────────────────────────────────────────────────────────────┘
```

**Главный принцип:** интеллект — у Claude (лучшая модель, видит контекст
вопроса). Сервер — быстрый и дешёвый поставщик материала. Библиотекарь
приносит книги, аналитику пишет аналитик.

## 3. Слой 1 — backend-движок

### 3.1. Что хранит — модель данных

**SQLite** (`khronika.db`):

| Таблица | Что | Кто пишет |
|---|---|---|
| `documents` | документ: id, title, status, file_path, file_hash, parsed_text, brief | индексатор |
| `chunks` | куски документов (текст + раздел + позиция) | индексатор |
| `entities` | извлечённые метрики/проекты/люди/даты | extract_entities |
| `numeric_contradictions` | числовые расхождения (карточки) | детекторы |
| `logic_signals` | логические расхождения (карточки) | детекторы |
| `promises` | обещания + статус (open/overdue) | track_promises |
| `document_relations` | связи документов | build_graph |
| `chat_messages` | история диалогов | API чата |
| `style_feedback` | правки пользователя к сгенерированному тексту (original/edited/diff) — обучающий сигнал для стиля | API написания |

Всего 9 таблиц.

**ChromaDB** (`data/chroma`): коллекции `khronika_actual` / `khronika_archive`
— векторные представления кусков для поиска по смыслу.

### 3.2. Что делает движок

- **Хранение** — документы, их распарсенный текст.
- **Чанкинг** (`rag/chunker.py`) — режет документ на куски, таблицы режет
  с переносом заголовка.
- **Эмбеддинги** (`clients.py`) — локальная модель `sentence-transformers`,
  **не LLM-вызов**, без интернета.
- **Retrieval** (`rag/retriever.py`) — гибридный поиск: вектора + BM25 +
  RRF-слияние + boost по иерархии + дедуп + раздача долей по документам.
- **API** (`api/`) — HTTP-эндпоинты, в т.ч. `/api/retrieve` (чистый поиск
  без LLM), `/api/documents/{id}/text` (полный текст).

### 3.3. Чего движок НЕ делает (по целевой архитектуре)

- Не синтезирует ответ — это Claude.
- Не пишет документы, не ищет в интернете — это Claude.
- Целевое состояние: **на живом пути запросов — ноль LLM-вызовов**.

### 3.4. Два пути и изоляция серверного «мозга»

В коде сосуществуют два пути — их нельзя путать:

- **Целевой (продуктовый) путь** — `Claude → veyra-mcp → слой данных`.
  Слой данных движка: `GET /api/retrieve` (чистый поиск) и data-эндпоинты
  (`/api/documents`, `/api/contradictions/*`, `/api/promises`,
  `/api/docs/stats`). Ноль LLM на сервере. Рассуждение — у Claude по
  плейбуку `veyra-skill/SKILL.md`.
- **Legacy путь** — `POST /api/chat` → `orchestrator` → `docs-agent`.
  Серверный «мозг»: синтез ответа делается на сервере (LLM на живом
  пути). Используется **только React-админ-панелью**, продуктовым путём
  не является.

Серверный мозг **изолирован**: гейтится флагом `ENABLE_LEGACY_CHAT`
(по умолчанию `True` — панель работает). В production-деплое без панели
ставится `ENABLE_LEGACY_CHAT=0` — `POST /api/chat` отдаёт 404, остаётся
чистый слой данных. `orchestrator.py` и `docs.py` помечены `LEGACY` —
не развивать; вся новая логика рассуждения идёт в `SKILL.md`.

---

## 4. Слой 2 — veyra-mcp

Тонкий MCP-фасад. На живом пути **не вызывает LLM** — только подаёт данные.
8 инструментов:

| Инструмент | Отдаёт | Источник |
|---|---|---|
| `search_corpus(query, top_k)` | релевантные фрагменты документов (сырьё) | `/api/retrieve` |
| `get_document(doc_id)` | полный текст одного документа | `/api/documents/{id}/text` |
| `list_documents()` | список документов корпуса | `/api/documents` |
| `find_numeric_contradictions()` | таблица числовых расхождений | `/api/contradictions/numeric` |
| `find_logic_contradictions()` | таблица логических расхождений | `/api/contradictions/logic` |
| `find_open_promises()` | таблица незакрытых обещаний | `/api/promises` |
| `corpus_stats()` | сводка по корпусу | `/api/docs/stats` |
| `health()` | доступность движка | `/health` |

Все — быстрые, детерминированные, без расхода токенов. Транспорт —
streamable-http; разворачивается на PaaS, регистрируется в Avito mcp-hub.

---

## 5. Слой 3 — Claude (агентный цикл)

Claude — весь интеллект. Получив вопрос, он не ждёт готовый ответ от
сервера, а **итеративно докапывается**, как исследователь в библиотеке:

```
вопрос
  │
  ├─ search_corpus("тема")        → увидел релевантные куски
  ├─ search_corpus("метрика M")   → нашёл документ с другим значением
  ├─ get_document(id)             → вчитался в документ целиком
  ├─ find_numeric_contradictions  → сверил с предвычисленными карточками
  │
  └─ рассуждение → ответ с цитатами
```

`SKILL.md` (`veyra-skill/`) — **плейбук**: инструкция Claude, как из этих
данных проверять инициативу, искать пробелы, сверять корпус с рынком
ради «неувиденного», писать grounded-черновик. Skill публикуется в
Avito skills-hub.

## 6. Потоки

### 6.1. Загрузка документа (индексация)

```
документ → парсинг → чанкинг → эмбеддинги → ChromaDB + SQLite
                                          → детекторы → карточки (SQLite)
```
Два пути загрузки:
- **`POST /api/documents`** (upload / drag-drop) — индексирует в процессе
  сервера, сервер сразу видит новое. **Правильный путь для живого сервера.**
- **`index_docs.py --sync`** — отдельный процесс, инкрементальная
  до-загрузка; после неё сервер перезапустить (иначе ChromaDB-клиент не
  увидит новые куски). Для bulk-загрузки.

### 6.2. Интерактивный запрос

Сотрудник → его Claude → (MCP) → veyra-mcp → (HTTP) → движок отдаёт
данные → Claude рассуждает агентно → ответ с цитатами.

### 6.3. Проактивный обход (план)

Claude по расписанию (n8n, раз в сутки) проходит корпус, ищет новые
расхождения, постит дайджест в Mattermost. Это тот же Claude, просто
запущенный по cron — не серверный детектор.

## 7. Масштаб: 3 → 500 документов

**Случай A — конкретный запрос** («проверь инициативу X»). Масштабируется:
retrieval сужает 500 документов до ~15 релевантных кусков, Claude читает
ограниченный срез, докапывается итеративно. Риск — качество retrieval на
масштабе (см. §11).

**Случай B — «найди ВСЕ противоречия в корпусе».** Сравнить всё со всем =
~125 000 пар на 500 документах — невозможно ни для какой архитектуры.
Решение — **кластеризация**: противоречие бывает только между
документами про одно и то же. Сервер держит дешёвый структурный индекс
«метрика/тема → какие документы её касаются» (метрики — регексом, темы —
кластеризацией по эмбеддингам, почти без LLM). Проактивный обход Claude
идёт **по кластерам** — сотни фокусных сверок вместо 125 000.

Граница: сервер индексирует «что-чего-касается» (дёшево). Claude судит
«что-чему-противоречит» (дорого, умно).

## 8. Что система МОЖЕТ и что НЕ МОЖЕТ

**Может:**
- Находить числовые и логические расхождения между документами и внутри
  документа — с цитатами, без видимых галлюцинаций (показано гейтом:
  4/5 на малом корпусе в full-text режиме, один прогон — см.
  `gate_report.md`).
- Находить невыполненные обещания (обещал/сделал).
- Находить пробелы (4a) — что обсуждали, но не закрыли планом.
- Отвечать «что мы уже знаем про X», сверять новую инициативу с корпусом.
- Помогать писать документ (grounded-черновик) — силами Claude поверх
  данных Veyra.

**Сможет (Возможность 4b, после Фазы 2):** отвечать «чего мы не видим» —
сверкой корпуса с рынком и дашбордами. Сейчас из корпуса выводятся
только пробелы (4a); «неувиденное» требует внешних рамок (см. §9).

**Не может (пока / по дизайну):**
- ❌ Дашборды — «какие метрики мы не смотрим» (Возможность 7, не построено).
- ❌ Мгновенный корпусный обход — проактивный поиск это batch по
  расписанию, минуты, не миллисекунды.
- ❌ Гарантировать полноту на retrieval — если поиск не поднял нужный
  кусок, находка пропущена (см. риски).
- ❌ Заменить человека — выдаёт находки и черновики, решение за человеком.
- ❌ Работать без корпуса — на пустой базе бесполезна.

## 9. Что реализовано СЕЙЧАС vs ЦЕЛЬ

| Элемент | Сейчас | Цель |
|---|---|---|
| Хранение/чанкинг/эмбеддинги/retrieval | ✅ работает | без изменений |
| `/api/retrieve` (чистый поиск) | ✅ есть | без изменений |
| veyra-mcp (8 data-инструментов) | ✅ есть, проверен импортом | прогон с живым Claude |
| veyra-skill (плейбук) | ✅ черновик | доработать под пилот |
| Индексные детекторы (extract_entities, find_logic_signals, find_intra_contradictions, track_promises) | ⚠️ **есть, работают, но слабые** | заменить кластер-индексом + агентным Claude |
| Структурный индекс (метрика/тема → документы) | ❌ не построен | построить для случая B |
| Дашборды (Возможность 7) | ❌ не построено | Фаза 2 |
| Деплой на PaaS + mcp-registry | ❌ | Фаза 2 |

**Честно про детекторы.** Сейчас на индексации работают LLM-детекторы,
пишут карточки в таблицы `numeric_contradictions` / `logic_signals` /
`promises`; veyra-mcp отдаёт эти таблицы как данные. Целевая архитектура
— заменить детекторы дешёвым структурным индексом + агентным Claude
(детектор слабее Claude — доказано: 0/0/0, затем шумные 14 в одном
документе). **Детекторы НЕ удалены сознательно:** удалять старое до того,
как готова и проверена замена (структурный индекс) — неверная
последовательность. Уберутся, когда замена построена и проверена.

## 10. Стоимость (модель расхода токенов)

- **Живой путь veyra-mcp — 0 токенов.** Поиск/чтение — локальные
  эмбеддинги и БД, без LLM.
- **Рассуждение — на подписке Claude** пользователя (его помощник).
- **Индексация** — LLM-расход при загрузке документа (детекторы, бриф).
  Разово на документ. В целевой архитектуре сокращается.
- **Проактивный обход** — batch-расход Claude по расписанию.

Это и есть устойчивая модель: сервер не жжёт токены на запросах, расход
там, где он естественен — на стороне Claude.

## 11. Открытые риски

1. **Retrieval на масштабе не проверен.** Гейт прогонялся на 3
   документах. На 500 — recall неизвестен. Митигируется инкрементальной
   загрузкой батчами с перепрогоном гейта после каждого.
2. **Тихий ложный негатив.** Если retrieval не поднял нужный кусок,
   Claude ответит «расхождений нет», хотя они есть. Митигация — каждый
   ответ несёт охват проверки; «чисто» без охвата запрещено.
3. **Структурный индекс — нормализация.** Кластеризация по метрикам
   зависит от того, одинаково ли названа метрика в разных документах.
   Несовершенно.
4. **veyra-mcp не прогонялся против живого Claude** — рукопожатие MCP
   проверено только импортом.
5. **Качество вердикта/написания** не покрыто детекторным гейтом — это
   генерация, нужна своя проверка.
6. **SQLite** — конкурентная запись мультиюзера; на масштабе — Postgres.

## 12. Безопасность и конфиденциальность

Корпус — конфиденциальные стратегические документы. Индекс с
эмбеддингами и любые выгрузки метрик — производное от конфиденциальных
данных (ТЗ, Принцип 5). Отсюда требования к архитектуре.

**Аутентификация.**
- Движок (Слой 1) поддерживает bearer-токен через настройку
  `API_AUTH_TOKEN`. Если он задан — запросы без `Authorization: Bearer …`
  отклоняются. `veyra-mcp` передаёт токен из своей переменной
  `VEYRA_BACKEND_TOKEN`.
- В production `veyra-mcp` (Слой 2) закрывается авторизацией Avito
  mcp-hub / Keycloak — звать инструменты могут только авторизованные
  пользователи. На этапе alpha доступ — только разработчикам.

**Хранение данных.**
- ChromaDB и SQLite размещаются только в авторизованном сервисе на
  PaaS Avito. Запрещено: публиковать индекс в общий S3, класть базу
  локально у пользователей (ТЗ, Принцип 5).
- Текущий dev-режим (локальные ChromaDB + SQLite, личный ключ LLM) —
  только для разработки и гейта; это **не** целевой режим хранения.

**Внешние вызовы.**
- В веб-поиск (рыночный контекст) запрещено отправлять сырой текст
  конфиденциальных документов — только обобщённые тематические термины
  (ТЗ §3.5).
- LLM в production — через Avito LLM Gateway, не напрямую в Anthropic
  (ТЗ §8).

**Защита от prompt-injection.** Текст загружаемого документа
оборачивается в служебный тег и проверяется на инъекционные паттерны;
подозрительные инструкции игнорируются и помечаются в `warnings`. Это
defense-in-depth (эвристика), не строгая гарантия.

## 13. Резюме

Veyra = **глупый быстрый сервер (хранение + поиск + дешёвый индекс) +
агентный Claude (весь интеллект)**. Сервер приносит материал, Claude
рассуждает. Доставка — через MCP внутри помощника сотрудника.

Показано (один прогон, full-text, малый корпус): Claude находит
размеченные расхождения с цитатами, без видимых галлюцинаций.
Не доказано: масштаб 500 (retrieval), precision, живой MCP-прогон,
дашборды. Следующий honest-шаг — токен gateway, инкрементальная
загрузка батчами, перепрогон гейта после каждого батча.
