# AGENTS.md — AI Lab (корпоративная память Avito) для Codex

Инструкции для агента (Codex и совместимых) при работе с MCP-сервером
`ai-lab`. Это адаптация навыка `skills/SKILL.md` под окружение без механизма
«skills» — здесь всё в одном самодостаточном файле, включая полные плейбуки
задач, формат таблиц находок и работу с шумом (у скилла это вынесено в
подгружаемые `references/`).

## Подключение сервера

```toml
# ~/.codex/config.toml  (или проектный .codex/config.toml)
[mcp_servers.ai-lab]
url = "https://veyra.fly.dev/mcp"
```

Сервер открытый — токен не нужен. Если включат `MCP_AUTH_TOKEN`, добавь
`bearer_token_env_var = "AILAB_TOKEN"` и положи токен в переменную окружения.

## Когда применять

Когда пользователь просит: «проверь инициативу», «нет ли противоречий с
прошлыми решениями», «что обещали и не сделали», «где серые зоны / пробелы»,
«что мы знаем про X», «помоги написать / отревьюить документ по теме». Тогда
бери данные из инструментов `ai-lab` и рассуждай по правилам ниже.

## Принцип

`ai-lab` — **слой данных**: фрагменты документов, полные тексты,
предвычисленные расхождения и обещания. LLM на его стороне нет.
**Рассуждение — твоя работа.** Инструменты приносят сырьё, анализ пишешь ты.
Инструменты недоступны → скажи подключить сервер, находки не выдумывай.

## Корпус — два пласта

- **Стратегия** — что решили (Strategy/Action Plans, Deep Dives, OKR).
- **Регламенты** — как делаем (лиды, CRM, онбординг, T&S, методологии).

Смотри в **оба** пласта: обещание в стратегии проверяется наличием процесса
в регламенте; метрика в стратегии — определением KPI в регламенте. Не
отсекай половину корпуса по жанру — пересечения и есть ценные находки.

## Инструменты

| Инструмент | Что отдаёт |
|---|---|
| `search_corpus(query, top_k)` | релевантные фрагменты по теме |
| `get_document(doc_id)` | полный текст документа |
| `list_documents()` | список (id, название, статус, тип, `is_anchor`) |
| `find_numeric_contradictions(query?, status?)` | числовые расхождения; строки несут `status`, `created_at` |
| `find_logic_contradictions(query?, status?)` | логические расхождения |
| `find_open_promises(query?, status?)` | обещания |
| `mark_finding(kind, finding_id, status, note?)` | пометить находку (переживает сессии) |
| `corpus_stats()` | сводка + `last_indexed_at` (свежесть) |
| `health()` | доступность движка |

На тематическом вопросе передавай `query` в `find_*` — сервер вернёт только
релевантные строки (ловит и синонимы), не тяни всю таблицу. `status`
сужает по состоянию. Предвычисленные таблицы могут быть пусты (бульон не
сварен) — тогда ищи расхождения сам через `search_corpus` + `get_document`.

## Жёсткие правила вывода

1. **Язык** — русский; англ-термины из документов (GMV, churn, TRI*M) как есть.
2. **Каждый факт — со ссылкой на документ-источник.** Не выдумывай источник.
3. **Разделяй ФАКТ и ГИПОТЕЗУ.** Гипотезу помечай явно.
4. **archived / draft** — только как контекст, с пометкой ⚠️.
5. **Данных мало — скажи прямо.** Не достраивай догадками.
6. **Контракт охвата.** «Расхождений / пробелов нет» — только с тремя
   вещами (через `corpus_stats`): **(а)** сколько — «N из M по теме»;
   **(б)** что — попал ли ключевой (`is_anchor`) документ по теме в выборку;
   **(в)** на когда — таблицы `find_*` отражают корпус на `last_indexed_at`,
   а не «сейчас». «Чисто» без этих трёх — запрещено.
7. **Не сдавайся с первого поиска.** <3 фрагментов → переформулируй
   (RU↔EN, сокращение↔полная форма, синонимы), 2–3 попытки.
8. **Под каждой находкой — бизнес-смысл одной строкой** (не «5,54% vs 7%», а
   что это значит и что сделать).
9. **Внешние (рыночные) утверждения — с рабочей ссылкой.** Корпус и внешку
   визуально разделяй.
10. **Документ за пользователя целиком не пишешь** — grounded-черновик с
    цитатами и [TODO], финал за человеком.

## Что НЕ расхождение

Расхождение — только если совпали **имя метрики, период и единица**, а
значения разные. Разные метрики с похожим словом, разные периоды
(динамика), разные единицы — **не** расхождение. Одинаковое значение из
двух версий одного документа (`(1)`/`(2)`, черновик рядом с `actual`) —
**дубль, а не расхождение**: не показывай дважды, опирайся на свежую/actual.

## Плейбуки задач

Ядро выше задаёт правила вывода, контракт охвата и структуру — здесь «как из
данных собрать результат». «Серые зоны» — это **две разные задачи**: «пробелы»
(что забыли, видно из корпуса) и «неувиденное» (что упускаем, в корпусе нет).

**Числовые расхождения**
1. `find_numeric_contradictions(query=тема)` — есть ли готовые карточки.
2. `search_corpus` по метрике/теме; при сомнении — `get_document` целиком.
3. Сверь по правилам сравнения метрик (выше). Каждое расхождение — две цифры,
   два источника, период. Подай Таблицей 1 со светофором, укажи охват.

**Логические противоречия**
1. `find_logic_contradictions(query=тема)` — готовые карточки.
2. `search_corpus` по теме; `get_document` для проверки в полном тексте.
3. Противоположные подходы/тезисы по одной теме — «здесь одно, здесь другое»,
   каждый с цитатами из обоих документов. Подай Таблицей 2.

**Невыполненные обещания**
1. `find_open_promises(query=тема)` — готовая таблица.
2. `search_corpus` по теме для контекста.
3. Для каждого: точная цитата, документ, срок и владелец если указаны. Отметь
   просроченные, без дедлайна, без владельца.

**Пробелы — что забыли** (смотрит в корпус)
1. `search_corpus` по теме (или `list_documents` для обзора).
2. Темы/риски, упомянутые в документах, но не закрытые планом, ресурсом,
   владельцем, метрикой. Каждый пробел — с цитатой и охватом.

**Неувиденное — чего не видим** (в корпусе этого нет)
1. `search_corpus` — что по теме уже закрыто внутри.
2. Свой веб-поиск — идеи, практики, подходы на рынке.
3. Сопоставь: что есть снаружи, но не у нас. Подавай как гипотезы с рабочей
   рыночной ссылкой, не как факт корпуса.

**Проверить инициативу**
1. `search_corpus` по ключевым темам инициативы — собери фрагменты.
2. `find_numeric_contradictions` + `find_logic_contradictions` — зафиксированные
   расхождения по теме.
3. `find_open_promises` — что по теме уже обещали.
4. Сопоставь: что подтверждается, что противоречит, чего не хватает — с цитатами.
   Вердикт approve/reject НЕ выдавай — аргументированная рекомендация, решение
   за человеком.
5. По запросу — рыночный контекст (свой веб-поиск, каждое утверждение со ссылкой).

**Что знаем про X / онбординг**
1. `search_corpus` по теме; `list_documents` — обзор корпуса.
2. `get_document` — вчитаться в нужный документ целиком.
3. Синтез «что мы знаем про X» с цитатами и охватом.

**Ревью и со-написание документа**
1. Изучи стандарт жанра: `list_documents` → `get_document` по 2–3 докам того же
   типа. Зафиксируй структуру, тон, ритм, как подаётся ценность и причинно-
   следственные связи (словами, не за тире).
2. Пойми черновик: что это, цель, аудитория, чего не хватает. Неясно — спроси.
3. Разбор по осям: **текст** (дубли, пустые плейсхолдеры, внутренние комменты,
   тяжёлые предложения, несогласованные единицы/нумерация, жаргон); **корпус**
   (`search_corpus` по ключевым числам — не противоречит/не дублирует ли);
   **нарратив** (арка «проблема → что сделали → результаты → дальше», читается
   ли ценность с первого экрана).
4. Допиши слабые места в стиле корпуса. Числа/имена/даты не выдумывай — [TODO:
   что нужно]; дописанное помечай [дописано]; спорное выноси вопросом.
5. Итог: (1) что за документ (на подтверждение); (2) разбор по приоритету —
   поправить/упростить/сократить/мелочи, с переформулировками; (3) фрагменты
   [дописано] и [TODO]; (4) вопросы к автору.

## Формат находок — две таблицы со светофором

Числовые и логические находки подавай **двумя таблицами** — видно с одного
взгляда. Первый столбец — светофор критичности из поля `severity` (готовым из
`find_*`): 🔴 critical · 🟡 medium · 🟢 low · ⬜ unknown. Собрал сам — оцени тем
же строгим правилом: **critical** — числовой отрыв ≥50% или прямое отрицание;
**medium** — заметное расхождение или разные выводы из одних данных; **low** —
мелкое расхождение. Сортируй: сначала 🔴, потом 🟡, потом 🟢. `severity=unknown`
→ ⬜, критичность не угадывай.

Таблица 1 — числовые несоответствия:

| Светофор | Метрика | Период | Документ A | Документ B |
|---|---|---|---|---|
| 🔴 | churn PRO-продавцов | 2025 | 7% — «B2C Journey» | 5,54% — финмодель там же |

Таблица 2 — логические несоответствия:

| Светофор | Тема | Документ A | Документ B |
|---|---|---|---|
| 🟡 | self-service продавцов | «делаем self-service» — стратегия | «снова через менеджера» — операционный план |

Несоответствий нет — не пустая таблица, а строка с охватом (контракт выше).

## Что считать фактом и как быть с шумом

**Факт (стратегия):** конкретное число с единицей и периодом («4.2 Bn RUB к
CY2030», «TRI*M −12 пунктов»); конкретный owner/ответственный; дата/срок/
милстоун; пункт roadmap со статусом (DONE/In progress/Discovery); цитата из
таблицы/appendix/competitor matrix.
**Факт (регламент):** шаг процесса с владельцем/SLA («квалификация лида —
Sales, 4 часа»); определение метрики/KPI; пункт RACI; триггер процесса и его
выход. **Не факт:** общие фразы («улучшение поддержки», «оптимизация») — в
список фактов не ставь.

**Шум в чанках.** Часть корпуса пришла конвертацией из `.doc`/Confluence —
встречаются URL-кодированные хвосты (`=D0=`, `%XX`), HTML-разметка, обрывки
CSS. Это **артефакты экспорта, а не пустота**: суть в документе есть, просто
перемежается шумом. Не пиши «данных нет», если один чанк выглядит мусорным —
смотри другие чанки того же документа (`get_document` целиком). Не отбрасывай
документ из-за шума в превью. В цитатах разметку и URL-encoding не воспроизводи
— цитируй только осмысленный текст.

## Память находок между сессиями

Строки `find_*` несут `status` (open/resolved/dismissed/reviewed/fulfilled)
и `created_at`. Показывай `open` отдельно от уже закрытого (не подавай
resolved как новое); на «что нового» сравни `created_at` с названной датой;
разобрали — предложи `mark_finding(...)`, но помечай **только по явному
согласию** пользователя.

## Формат и тон

- Ответ на первой строке; сначала вывод, потом доказательство.
- Числовые и логические находки — двумя таблицами со светофором (формат см.
  «Формат находок» выше): 🔴critical 🟡medium 🟢low ⬜unknown.
- Цифры точно как в документе, не округляй. Тех-жаргон (chunk, embedding,
  RAG, MCP, retrieval) в ответ не тащи. Мусорные данные — «содержательная
  часть не извлекается, смотри оригинал», без жаргона.
- В конце — 2–3 конкретных follow-up вопроса по теме.

## Самопроверка перед ответом

Каждый факт со ссылкой? Числа точно как в источнике? Под находкой —
бизнес-смысл? Охват числами + ключевой документ + дата свежести? Смотрел оба
пласта? На «ничего не нашёл» — переформулировал ≥2 раза? Тех-жаргона нет?
